# 翻译与大模型对话：可复用第三方方案选型

> 承接 `Doc/AI翻译与大模型对话集成可行性分析.md`（那份回答的是"能不能做、用什么地基"）。
> 本文档回答的是另一个问题：**有哪些现成的开源项目可以直接拿来用，哪些必须自己写。**
> 结论：翻译与对话这两件事，**都不需要从零写模型或推理引擎**；真正需要自己写的只有三块——鉴权签名、UI 与取值/取词流程。

## 0. 先看 tpix 已经有什么（决定了候选方案的成本）

这三条是本次选型的分水岭，很多看起来很贵的方案在 tpix 里其实是"增量"而非"从零"：

| 已有资产 | 位置 | 对本次的意义 |
|---|---|---|
| **已链接 `onnxruntime.lib`**，PostBuild 把 `onnxruntime*.dll` 拷到 exe 同目录 | `Src/tpix.vcxproj:131,139` | 端侧推理运行时**已经在**。加生成式能力不必再引一整套新运行时，顺势即可 |
| **已有一整套"按需下载 ONNX 模型"范式** | `Src/Table.cpp:52-80, 83-120` | `HttpClient::GetBufferAsync` → 体积合理性校验 → 写 `.downloading` 临时文件 → `rename` → `Ort::Session`；token 表从模型元数据读。本地 LLM 模型不过是同一条路上更大的一个文件 |
| **模型从 ModelScope 拉**（非 HuggingFace） | `Src/Table.cpp:24` `modelscope.cn/models/RapidAI/RapidTable` | 国内用户首次下载体验已验证可行，LLM 模型同样应该走国内镜像 |
| **WinRT `HttpClient` + `Windows.Data.Json`**（`windowsapp.lib` 已链） | `Src/Update.cpp`、`Src/Table.cpp` | 云 API 调用、流式响应解析都是现成能力，**不需要任何第三方 HTTP 库** |
| 许可证：**MIT**，C++20，x64 | `LICENSE`、`Src/tpix.vcxproj` | 引入 MIT / Apache-2.0 依赖无障碍；但 **GPL / LGPL / MPL 需谨慎** |

另注：当前**未链接任何加密库**（全仓 grep `bcrypt` / `crypt32` / `Crypt*` 零命中），火山翻译的 HMAC-SHA256 签名仍需补（上份文档已给出两条零新增组件的解法）。

## 1. 候选清单：推理引擎（做对话，或兼做翻译）

### 1.1 `microsoft/onnxruntime-genai`（OGA）— **首推**

| 项 | 内容 |
|---|---|
| 许可证 | **MIT** |
| 形态 | C / C++ / C# / Python / Java API；Windows x64 支持（官方支持矩阵：Model 架构含 Phi、Llama、Qwen、Gemma、Mistral、Whisper；硬件加速含 **CPU / CUDA / DirectML / QNN / OpenVINO**） |
| 它替你做什么 | 完整生成循环：prompt 拼装、tokenizer（自带，不用自己接 SentencePiece）、ONNX Runtime 推理、**logits 处理、采样搜索、KV cache 管理**、streaming 逐 token 吐出、以及 tool calling 的语法约束解码 |
| 与本项目的契合 | **直接复用已经那份 ORT 运行时**与 dll 拷贝流程；官方已有现成的 INT4 量化模型可直接 download（如 `microsoft/Phi-3-mini-4k-instruct-onnx` 的 `cpu_and_mobile/cpu-int4-rtn-block-32-acc-level-4`）；**一份模型同时承担"翻译"和"对话"两个功能** |
| 成本 | 需新增 `.lib`/`.dll`（OGA 的原生产物在 GitHub Releases 包，非规范 NuGet 原生包）；**OGA 与 ORT 版本强绑定**，可能与现有 ORT 版本冲突；模型 0.5–2.5 GB 量级，必须走"首次按需下载 + 进度 UI" |
| DirectML 的意义 | 这是它在 Windows 上胜过 llama.cpp 的一点：DirectML 是 Windows 通用 GPU 加速路径，N卡/A卡/I卡/核显同一份二进制即可受益，不必为每家编一套 CUDA/HIP/SYCL 变体 |
| 结论 | **首选**。和现有地基重合度最高，且能把"翻译"与"对话"收敛成一个引擎 |

### 1.2 `ggml-org/llama.cpp` — 生态最广的备选

| 项 | 内容 |
|---|---|
| 许可证 | **MIT** |
| 形态 | C/C++，无 Python 运行时依赖；CPU(AVX2/AVX512)、CUDA、Metal、Vulkan、ROCm、SYCL；GGUF 格式，量化档位从 Q8_0 往下到近 1.5 bit；安装体积 < 90 MB |
| 两种接法 | **① 进程内**：链接 `llama.h`/`libllama`，细粒度控制，流式回调天然可做；<br>**② 子进程起 `llama-server`**：它暴露 **OpenAI 兼容 HTTP 接口**，于是本地推理与云端调用可以**共用同一套 HTTP 客户端代码** —— 这条路径下"云/本地"的差别被压缩成 `base_url` 不同 |
| 优势 | GGUF 是目前社区最大的本地模型分发格式，中文模型（Qwen 系列、各类社区量化）选择远多于 ONNX |
| 成本 | 需要独立 CMake 构建产物并随包分发；GPU 后端要么编 Vulkan 要么编 CUDA，多套二进制管理成本高；进程内接法要自己写生成循环（虽然比从零写 DSP 层少很多） |
| 结论 | **次选，但"子进程跑 llama-server"这条路线非常值得作为 fallback** —— 它能让 simplify 到极致：UI 只需要一套 OpenAI 兼容客户端 |

### 1.3 `OpenNMT/CTranslate2` — 若要求"专用翻译，体积也小"

| 项 | 内容 |
|---|---|
| 许可证 | **MIT**（2019 由 GPL 切 MIT） |
| 维护状态 | **活跃**：v4.8.2 于 2026-08-31 发布，2026 年内连续发布 v4.7.x / v4.8.x |
| 覆盖面 | 编码器-解码器：Transformer base/big、**M2M-100、NLLB**、BART、mBART、T5、Whisper 等；纯解码器：Llama、Mistral、Gemma、**Qwen2**、GPT-2/OPT 等 —— 也就是说**它同样能一库两用** |
| 优势 | int8 量化下 GPU/CPU 都很省；顺序/去重/层融合等优化是它的立项动机；模型量化后磁盘占用可降到 1/4 |
| 成本 | **C++ 使用需自行 CMake 构建 Windows DLL**（Python 有 wheel，C++ 没有官方预编译便利途径）；模型必须先经 `ct2-*-converter` 转换，或找现成转换好的包 |
| 结论 | 当"离线翻译质量要好、模型体积又要小（几百 MB 级）"时才优先考虑；否则 OGA 更省事 |

### 1.4 `argos-translate` — 不直接嵌，但**白拿模型**

纯 Python 库（MIT，底层就是 CTranslate2），**不能直接嵌进 C++**。
它对本项目的价值是别的东西：它有完整的**语言包索引 + 已转换好的 CTranslate2 模型包**。
如果想走 1.3 那条路，可以直接取它现成的包喂给 CTranslate2，省掉自己转换模型这一步。

### 1.5 `mozilla/bergamot-translator` — **不推荐**

- 许可证 **MPL-2.0** —— 文件级 copyleft。tpix 是 MIT，混入 MPL 代码会带来持续的法务说明义务，和一个" MIT 小工具"的定位不符。
- 它的主要形态是 **emscripten/WASM**（给 Firefox 浏览器翻译用），Windows 原生 C++ 集成资料稀少。
- 模型确实很诱人：**每语种约 12–13 MB（欧语pair），中日韩pair 约 30–45 MB**，质量也有官方 BLEU/COMET 对比数据。
- 结论：如果某天真的要极致小的离线翻译，可以考虑**复现它的做法**（算子/marian 蒸馏 + intgemm），而不是引入它的代码。

### 1.6 直接使用现有 ORT 跑 OPUS-MT ONNX 模型 — 最低成本的试点

HuggingFace 上有由 `optimum` 导出的 OPUS-MT ONNX 模型（含 `onnx/model_quantized.onnx` 与 tokenizer）。
因为 **ORT 已经在项目里**，理论上"零新增依赖"就能跑起来离线翻译。
**但**：sentencepiece 分词 + beam search 贪心/束搜索解码循环 + 批量 padding，得自己写，约三五百行且容易出细 Bug。
结论：适合做两天量级的技术验证；正式落工程量大于直接上 OGA。

## 2. 候选清单：云端服务（保留，且应当是默认路径）

| 服务 | 特点 | 备注 |
|---|---|---|
| **火山翻译** | 现脚本已在用。需 **HMAC-SHA256 签名**（本项目目前无加密库，需补） | 已经是用户熟悉的链路 |
| **OpenAI 兼容网关**（通用） | OpenAI / DeepSeek / 硅基流动 / 各家兼容接口，协议同一套 | 一个重要事实：**Ollama 与 `llama-server` 也暴露这个协议** ⇒ 本地部署可以复用同一套客户端代码 |

⇒ 由此得到架构上的关键建议：**必须定义统一的 Provider 抽象**，把"云端 / 本机进程外服务 / 本机进程内引擎"收敛到同一个接口下。详见 §4。

## 4. 推荐架构：统一 Provider + 三后端

```
                 ┌──────────────────────────────────────────┐
 UI 层（自写）    │ 结果浮层 / 对话窗 / 设置页 / 翻译按钮        │
                 └───────────────────┬──────────────────────┘
                                     │  IAiService（自写，~200 行）
                 ┌───────────────────┴──────────────────────┐
 取值层（自写）   │ OCR 词框取词 / 模拟 Ctrl+C 取选中 / 用户输入  │
                 └───────────────────┬──────────────────────┘
                                     │
        ┌────────────────────────────┼────────────────────────────┐
        ▼                            ▼                            ▼
 ①云 OpenAIChatProvider   ②云 VolcanoTranslateProvider   ③LocalProvider
   HttpClient+Json           HttpClient + HMAC-SHA256      待定二选一：
   （现有能力）                （需补签名库）              A. 进程内 OGA
        ▲                                                  B. 子进程 llama-server
        │                                                     └── 内部复用 ①的 HTTP 代码
        └──── Ollama / llama-server 也走这条路 ─────────────────┘
```

**为什么这么切**：①与③-B 共用同一份 HTTP 代码；如果先用 ① 落地跑通，后面加本地引擎只需新增一个 Provider 实现，UI 与流式解析一行不改。

### 三个后端怎么选

| 维度 | ①云 API | ③-A 进程内 OGA | ③-B 子进程 llama-server |
|---|---|---|---|
| 新增依赖 | 无（仅缺签名库） | OGA lib + dll + 模型下载 | 新 exe + 模型下载 |
| 安装包增量 | 0 | 库体积 + 模型另下载 | ~数十 MB + 模型另下载 |
| 首次可用门槛 | 用户需自填 key | 首次下载 GB 级模型 | 同上 |
| 隐私（文本不出机） | ✗ | ✓ | ✓ |
| 实现工作量 | 最小 | 中 | 中 |
| 建议定位 | **默认** | 可选增强 | 可选增强 |

**推荐顺序：先做 ①，把 ① 的接口设计成将来能装 ③ 的形状；再按用户反馈决定要不要上本地。**

## 5. 不需要从零写的东西（这是本文档的核心答案）

| 能力 | 是否有现成方案 | 本项目要写的部分 |
|---|---|---|
| 模型 / 推理引擎 | ✅ OGA / llama.cpp / CTranslate2，全部 MIT | 只写调用层 |
| Tokenizer + 流式生成循环 | ✅ OGA 自带；llama.cpp 自带 | 无（选对库就免费） |
| HTTPS 请求 | ✅ WinRT HttpClient 已在用 | 无 |
| JSON 解析 | ✅ `Windows.Data.Json` 已在用 | 无 |
| 模型按需下载 | ✅ `Table.cpp` 现成范式 | 照抄，换 URL 与体积阈值 |
| 结果浮层 UI | ⚠️ Ling 有 `SelectPopup`/浮层范式 | 自写，但约半日量 |
| 多行输入框 | ✅ `Ling::TextBox`（含 IME、折行、滚动） | 布局而已 |
| 全局热键 | ✅ `Setting.cpp` 的 `shortcutDefs[]` 表 | 加一行表项 + 一个 `case` |
| HMAC-SHA256 签名（火山） | ⚠️ 无第三方库，但 WinRT `Windows.Security.Cryptography.Core` 随 `windowsapp.lib` 已链 | 自写约 60 行 |
| key 加密存储 | ⚠️ 同左，`DataProtectionProvider` 不用加库 | 自写约 30 行 |
| 翻译 / 对话 UI 与取值流程 | ❌ 无可直接复用者 | **必须自写**（这也是产品差异所在） |

⇒ 一句话：**3/4 以上的工作量可以被现有开源库替掉，剩下那 1/4 才是属于 tpix 自己的东西。**

## 6. 落地阶段（每阶段给可验证目标）

阶段划分沿用 `Doc/AI翻译与大模型对话集成可行性分析.md` 的 P1–P4 排序。

| 阶段 | 内容 | 可验证目标 |
|---|---|---|
| **S0 技术验证** | 1) WinRT Crypto 算出的火山签名与 AHK 脚本一致；2) OGA hello-world（Phi-3-mini CPU int4）在 MSVC 下链接通过、能逐 token 吐字 | 两个独立验证程序各自通过（验证完**删掉临时产物**，不进主工程） |
| **S1 云端对话** | 定义 `IAiService`；实现 ① OpenAI 兼容 Provider（含 SSE 流式）；做一个最小对话窗 | 填入任意 OpenAI 兼容 key 后，输入问题能流式收到并显示完整回答 |
| **S2 取词翻译** | 接 OCR 词框坐标取值 → 调 ① 的翻译 prompt；结果浮层 | 截一张英文图 → 选中某行 → 浮层显示中文译文且不遮挡原文 |
| **S3 云端翻译链** | 补 HMAC 签名 + 火山 Provider + key 加密存储 | 火山翻译与 OpenAI 两项并列可选；重启后 key 仍可用，落盘非明文 |
| **S4（可选）本地引擎** | 接 OGA 或 llama-server，新增一个 Provider 实现 | UI 层未改动一行，切换到本地模型后功能一致 |

## 7. 风险与必须先确认的事

1. **⚠️ 决策冲突（最高优先级）**：`Doc/竞品能力差距分析.md` 于 2026-10-01 已裁决 **D4「AI 翻译」不做**（理由：需持续在线服务投入 + 用户自填 key，非主干体验；并注明将来走"按需下载插件"）。本文档的任何推进都等于重启该决策，**需显式确认并同步更新那份文档的 §5 / §7.4**。
2. **模型权重许可证 ≠ 代码许可证**。代码 MIT，不代表模型可以随便分发：Qwen 系列 Apache-2.0、Phi 系列 MIT、**Gemma 有独立使用条款**。若随包或引导下载模型，须在设置页明确标注来源与条款。
3. **版本绑定**：OGA 对 ORT 版本有要求，现有 `D:\sdk\onnxruntime` 版本可能需要跟着升级，会影响已验证的表格识别模型 `slanet-plus.onnx`。建议先验证。
4. **体积与定位冲突**：tpix 是轻量截图工具。GB 级模型即使"按需下载"，也会显著改变用户的首次体验。建议保持"本地模型 = 可选项"。
5. **本地 CPU 推理速度未经实测**。文档提到的 token/s 数据均来自厂商/第三方资料，**本项目目标机型（无独显的普通办公机）上的实际速度必须在 S0 阶段实测**再决定是否上架本地能力。
6. **不要带入 AHK 脚本的明文日志习惯**（脚本把全部输入输出写 `logs/*.log`）——隐私红线。

## 8. 建议

- **翻译**：短期走**云 API**（火山翻译或让同一个 LLM 承担）；若要离线，优先 **OGA + 一份双向能力的小模型**，而不是引入专用 NMT 引擎。理由是**一库两用**（翻译+对话共用），能把维护成本砍半。
- **对话**：首选 **onnxruntime-genai**（复用现有 ORT，DirectML 在 Windows 上覆盖面最好）；若要更多模型选择或更快吃到新架构，走 **llama.cpp 的 llama-server 子进程**路线，协议上复用云端那套代码。
- **不要做的事**：不要自己写推理引擎；不要引入 **MPL-2.0** 的 bergamot；不要一开始就上本地模型（把 S1–S3 做完再回头看是否真的需要）。
- **待您裁决**：① 是否重启 D4？② S1–S3 是否照此顺序推进？③ 本地能力（S4）是否需要纳入本次范围？
