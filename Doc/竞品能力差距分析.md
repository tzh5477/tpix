# tpix 竞品能力差距分析

> 对比对象：**PixPin**（当前 3.5.x，Windows + macOS，免费 + 会员制）与 **FastStone Capture / FSCapture**（当前 11.2，Windows，商业授权）
> tpix 侧结论均基于本仓库源码核对（`Src/` 下 36 个头文件、33 个实现文件，约 7200 行），非依据 ReadMe 宣传口径。

---

## 一、结论先行

> **⚠️ 定位声明（已变更）**：本文初版以「守住 1MB 小巧」为前提，据此把 AI 翻译、公式识别、macOS 版等判为「不建议做」。**该前提已作废**——目标改为**对标 PixPin，最大限度实现其能力**，体积不再是约束条件。第七章路线图已按新目标重写；第四章、第五章中基于体积的论证也已相应修正。
>
> **⚠️ 范围声明（2026-10-01 用户裁决，2026-10-06 修订）**：目标虽是「对标 PixPin 全量」，但**本轮实施范围已明确收敛**——公式识别、macOS、UI 元素级检测、**F 组（FSCapture 方向编辑器与输出深化整组）**、录后视频编辑、GPU 硬编、脚本 API、深色模式不做；H6 标注工具补齐收敛为**仅水印**；**内置 OCR（G5）为必做项**。完整取舍见 **7.4 本轮范围裁剪**，那是唯一的实施依据。
>
> **⚠️ D4 已重启（2026-10-06 用户裁决）**：原判「不做」的 **AI 翻译**现已**解禁并扩充为「翻译 + AI 对话」**——翻译的交互形态参考 pot-desktop。同时明确：**只做云端在线服务，不做本地端侧推理**（不接 onnxruntime-genai / llama.cpp）。实施顺序为 **S1 云端对话 → S2 取词翻译 → S3 火山翻译链路**，详见 `Doc/翻译与大模型能力第三方方案选型.md` 与 D 组新的 D4 条目。

tpix 的基础链路（矩形框选 → 标注 → 钉图 → 导出）已经跑通，且工程质量有可圈点之处。但**它与两个竞品的差距不在"细节丰富度"，而在三个结构性缺位**：

1. **没有"贴图"这一层产品形态**。tpix 的 `WinPin` 本质上是"标注窗口"——单例、只能承接当次截图、`Ctrl+S` 即关窗。PixPin 的贴图是可长期驻留、可分组成(tag)、可承载文件/文本/颜色/LaTeX 的第二工作台。这是 tpix 与 PixPin 之间最大的产品代差。
2. **没有"编辑器"这一层**。tpix 只有标注图层叠加，没有裁剪、旋转、缩放画布、锐化、水印、边框/阴影/聚光灯等图像处理能力。FSCapture 在这一层的深度是 tpix 目前完全没有对应的。
3. **输出入口过窄**。导出仅有 PNG 一种格式 + 剪贴板一条通路，没有 JPEG/WebP/PDF，没有自动保存路径与命名模板，没有打印/邮件/Office/FTP 等目的地。

此外，**OCR 依赖外部 25MB 插件进程**（`Util::openWithImageReader` 用 `CreateProcess` 拉起 `ImageReader.exe`），这既是 tpix 保持 1MB 体积的取舍，也是 OCR 体验不可控的根源。

### 3.3 标注工具

tpix 有 8 个基础图形，且在"已绘元素可实时二次编辑"这一点上比 FSCapture 的固化标注更灵活（这是优势）。但工具种类与可配置项差距明显：

**缺失的标注工具**：画笔（自由笔迹）、荧光笔/高亮笔、多点折线（PixPin 支持 Tab 切换箭头）、放大镜标注（局部内容强调）、聚光灯、水印、callout 标注框、emoji/贴纸、算法aussian 模糊（tpix 只有马赛克）。

**缺失的样式能力**：
- 色板固定 9 色（`ToolSub::colors` 硬编码），无自定义色板、无取色器回写、无任意透明度调节
- 序号仅阿拉伯数字一种样式，不可手动增减编号，序号内不可填文字，外圈样式仅圆形气泡一种（PixPin 支持罗马/字母/中文数字 + 自定义前景色）
- 序号**已具备**箭头指向（`ShapeNumber::makePath` 的 `tip` 端点 + 角度夹点），此项不缺
- 文字无字体族选择（`ShapeText::makeTextLayout` 写死 Ling 的 baseTextFormat）、无字向旋转
- 马赛克无智能模式，仅矩形/自由涂抹两种（ToolSub 只暴露 1 个切换按钮）
- 矩形无圆角、无形变旋转；椭圆无扇形/弧形
- 线条无虚线样式；文本框无背景、无描边、无自动换行策略
- 无自定义标注按钮布局、无"记住上次工具"

> 以上标注入项的逐条改造方案与代码落点见**第六章**。

### 3.8 历史记录与内容管理

tpix **完全没有历史截图概念**（`History` 类只负责标注层的 undo/redo）。PixPin 保留历史截图（默认 100 张，上限 99999）、托盘可清理历史数据；FSCapture 用多标签 + 多工作区承担同样职责。这是"截图工具"与"工作流工具"的分水岭。

### 3.9 屏幕辅助工具

FSCapture 提供**屏幕取色器、屏幕放大镜、十字准线、屏幕聚焦、屏幕标尺**五个独立工具。tpix 只有截图界面内的取色放大镜——这是必要功能，除此之外全部缺失。tpix 的优势场景通常搭配 volumouse 之类的第三方工具使用，这是可以抢占的空白。

## 四、tpix 的既有优势（应当守住，不要照搬竞品）

1. **剪贴板兼容做得比两个竞品都细**：同时落 `CF_DIBV5`（带 alpha）、`CF_DIB`（24bpp 自下而上，专为旧软件）、`PNG` 三份数据，代码注释里明确记录了对 Illustrator 2020 的兼容处理。这类"兼容性脏活"是竞品文档里看不到的护城河。**（不因体积让步而失效）**
2. **标注元素可实时二次编辑**：`History` + `WinPin` 的悬停/拖拽/删除体系比 FSCapture 的"画上去就固化"灵活。**（PixPin 也没有做到这个粒度，是可守的差异点）**
3. **用完即走的进程模型**：`--auto-quit` + 命令行 `enter` 让其适合脚本化流水线，**这一点 PixPin 反而没有**。对标 PixPin 时不要把它改掉，应当保留并强化成脚本能力。
4. **二维码识别本地内嵌**（quirc），**两个竞品都干净缺失**，是 tpix 独有的差异化能力。
5. **开源免费 + 自研 GUI 框架（Ling）**：对比 FSCapture 的商业授权与闭源；且 Ling 与 tpix 同属 xland，**是可控上游而非外部依赖**——需要什么控件能力（字体族、拖放、旋转控件、flexWrap）直接改 Ling 即可，不存在等上游排期的问题。这一点在"对标 PixPin 全量"的目标下是最关键的工程优势。
6. ~~体积优势~~：**本项已随定位变更作废**，不再作为取舍依据。

## 五、补全优先级建议

### P0 — 决定产品竞争力的核心缺位（建议先做）

1. **多贴图 + 贴图来源扩展**：将 `WinPin` 从单例改为多实例管理；支持从文件、文本、剪贴板、颜色值创建贴图。这一步做完，tpix 才从"截图工具"变成"截图贴图工具"。
2. **输出格式与保存策略**：把 `encodePng` 抽象成编码器选择（JPEG / WebP / PNG），增加默认保存目录 + 命名模板 + `Ctrl+S` 直接落盘不弹窗。这是成本最低、感知最强的一块，建议最先动。
3. **历史截图面板**：复用现有抓屏 + PNG 编码，做列表 + 回查。数据存在 `%appdata%\tpix\history`。
4. **内置轻量 OCR**：不必追求 PixPin 的多语种 + AI 翻译，先做中文 + 英文的本地模型内联（哪怕体积增到 10MB 也仍远小于 PixPin），把"跨进程 + 需手动安装插件"的体验断点消掉。

### P1 — 明显提升专业感

5. **图片编辑基础能力**：裁剪、旋转、翻转、亮度/对比度、画布边框与阴影。这块是 FSCapture 的核心卖点，也是 tpix 目前 0 覆盖的领域。
6. **标注工具补齐**：画笔（缺了它几乎无法做批注类场景）、荧光笔/高亮、自定义色板（替换硬编码的 9 色）、序号多样式。按"简洁优先"原则，建议只做这四个，折线/扇形/emoji 暂缓。
7. **录制增强**：摄像头画中画、鼠标点击可视化、录制暂停。这三个投入产出比高，且不涉及视频编解码重构。

### P2 — 长尾补齐

8. 屏幕标尺 / 十字准线（低成本，锦上添花）
9. UI 元素级智能检测（成本高，且 tpix 的窗口级吸附已覆盖主流场景）
10. 输出到 Word / PPT / 邮件（国内用户实际使用率低）
11. 多语言宣发与深色模式

### 原判为「不建议做」的三项（**已随定位变更重新评估**）

> 以下三项在初版中因「守住 1MB 小巧」被否决。目标改为对标 PixPin 后，其中一项解禁，两项按用户裁决明确不做。

- **表格识别** → **改为「可做」**，见 7.2 阶段 D（D2）。技术选型见 7.4。

### 需求 1 — 马赛克支持智能擦除

**代码现状**：`Shape/ShapeMosaic.cpp`（520 行）已实现两种模式——矩形模式（`isRect`，8 夹点）与自由涂抹（路径 + 圆头描边，`strokeWidth` 来自滑块值域 18–68）。`buildMosaicBitmap` 负责按底图算出真正的马赛克画刷。`ToolSub::showMosaicTools()` 只暴露 1 个「矩形/涂抹」切换按钮 + 宽度滑块，**没有任何自动识别逻辑**。

**✅ 已澄清：要的是「背景色遮罩」——采样选区周围的背景色，用纯色盖住选区，视觉上让内容消失**

这与我之前猜测的两个方向都不同，而且**成本比两者都低**，属于「✅ 可直接做」。

**⚠️ 一个必须先讲清楚的事实**：tpix 现有的橡皮擦 `ShapeEraser` 里已经有一个叫 `initBackgroundBrush()` 的东西，但**它不是这个功能**。它的实现是 `CreateBitmapBrush(win->screenImg.Get(), ...)`——拿**原始底图**当画刷铺回去，效果是「把这块恢复成截图原样」（用于擦掉自己画的标注）。而你要的是「用背景色盖住，让原来的文字消失」，**两者效果正好相反**：一个还原内容，一个抹掉内容。这个命名极易误导，实现时务必区分开。

**改造路径**（可整体类比 `ShapeMosaic::buildMosaicBitmap` 的既有流程）：

1. **像素读回**：`ShapeMosaic::buildMosaicBitmap` 已有「把 GPU 位图读回内存算画刷」的完整先例，智能擦除复用同一条读回路径即可，不需要新造轮子。
2. **背景色推定（核心算法）**：推荐取**选区外扩 2px 环带内出现频率最高的颜色（众数）**；环带越界时退化为选区内众数。
   - 为什么用众数：你描述的「10 行文字」场景里，背景像素占绝大多数，文字边缘的抗锯齿灰度像素数量远少于背景，众数会稳定命中背景色。
   - 备选（更省事但更脆）：取选区四角像素的平均值。在纯色背景（白底文档）上完全够用，但在渐变/表格底纹上会明显露馅。
3. **填充**：矩形模式 `FillRectangle(rect, solidBrush)`；涂抹模式 `DrawGeometry(path, solidBrush, strokeWidth, roundStyle)`。
   - **⚠️ 涂抹模式的已知瑕疵**：用纯色画笔描边时，圆头描边的抗锯齿边缘会透出底下文字的残影，表现为「擦除区域边缘有一圈脏边」。要么接受它，要么把涂抹模式也改成沿路径的实心多边形填充。**矩形模式没有这个问题**，建议先只做矩形模式。
4. **UI 落点**：`ToolSub::showMosaicTools()` 现在只有「矩形/涂抹」一个切换按钮，需要扩成三态（矩形马赛克 / 涂抹马赛克 / 智能擦除）。或者更清晰的做法：在 `ToolMain` 的按钮组里新增一个独立工具。

**成本**：中等。核心算法约 60–80 行（众数统计 + 画刷构建），加上 UI 三态切换。

**建议**：先只做**矩形模式**的智能擦除，把涂抹模式的边缘瑕疵留到有反馈时再处理。

### 需求 2 — 悬浮球 / 常用工具贴边展示 + 拖拽自动贴图

**代码现状**：`Tray.cpp` 仅两个菜单项（设置/退出）。没有任何常驻悬浮 UI。

拆成两件事，可行性差别很大：

**（a）悬浮球本体 — ✅ 可直接做，成本低**
新增一个 `Ling::WinBase` 派生的小窗口（贴边吸附、可拖动、点击触发截图/贴图/长截图/录屏的快捷入口）。工程结构上参考 `ToolCap`（106 行）即可，是一个独立新文件，不侵入现有模块。注意 `App::excludeFromCapture(hwnd)` 要挂上，否则它会被自己的截图和录屏拍进去。

**（b）拖拽图片/文本到悬浮球自动贴图 — ⚠️ 可行但需先决条件**
两个前置：
1. **`WinPin` 必须先从单例改成多实例**（P0-1）。当前 `WinPin::hasWindow()` 是单例判定，`init`/`initFromData` 是静态工厂，一次只能存在一张贴图。「拖一张图进来变成一张贴图」在多实例之前无从谈起。
2. **需要 OLE 拖放目标**。要注册 `IDropTarget` 并处理 `CF_HDROP`（文件）与 `CF_UNICODETEXT`/`CF_TEXT`（文本）。
   源码里未见任何 `RegisterDragDrop` / `IDropTarget` 调用，即 Ling 目前不具备拖放能力。**但 Ling 是 xland 自研框架（与 tpix 同一作者），属于可控上游**——直接在 Ling 里加一层 `IDropTarget` 封装即可，不存在"等上游"的问题。这也同样适用于字体族、flexWrap 等其它 Ling 缺口（见 7.1 的 G4）。

**额外风险提示**：PixPin 官方文档明确写了「若需要使用悬浮球的拖动贴图功能，受限于 Windows 进程防线保护（UIPI），请取消勾选以管理员身份运行」。tpix 若支持以管理员运行，拖拽在低完整性级别的来源（多数普通进程）会被系统阻断。这一点建议在实现时直接提示用户，不要等用户来报 bug。

### 需求 3-1 — 文字工具：字体样式选择 + 竖排

**代码现状**：`Shape/ShapeText.cpp` 的 `setAttr()` 只取四样：颜色、字号（`toolSub->getSliderVal()`）、粗体、斜体。`makeTextLayout()` 调用 `Ling::D2D::get()->makeTextLayout(text, fontSize)`，**完全写死了 Ling 的 baseTextFormat，没有字体族参数**。

**（a）字体族选择 — ⚠️ 可行，取决于 Ling 的上游支持**

- 数据侧无难度：`EnumFontFamiliesEx` 枚举系统字体填下拉即可。
- 渲染侧需要两处同步：编辑态是 `Ling::TextBox`（`ToolMain.cpp` 里已有 `setFontFamily(L"icon")` 用法，说明 **TextBox 支持字体族**），导出态是 `IDWriteTextLayout::SetFontFamilyName`。
- **⚠️ 关键假设（需确认）**：`Ling::D2D::makeTextLayout` 是否接受字体族参数。若不接受，需改 Ling 仓库——这是**外部依赖**，有上游协作成本，`Src/` 里改不了。

**（b）任意角度旋转 — ✅ 已澄清为「整块旋转」，且要支持任意角度（参考 PixPin 编辑框的旋转手柄）**

不是逐字竖排，是**编辑框整体绕中心旋转，带动文字内容一起转，通过拖拽旋转手柄支持任意角度**。90° 只是其中一个特例。

**改造路径**：

1. **旋转数学已有现成参考**：`ShapeNumber` 的 `transformPoint()` / `localPoint()` 以及 `angle = -atan2(y-cy, x-cx)` 的角度夹点逻辑（`hoverDraggerIndex == 1`）是一套跑通了的旋转实现，直接照搬。
2. **渲染**：`ShapeText::paint` 里对 `DrawTextLayout` 应用 `D2D1::Matrix3x2F::Rotation(angle, center)` 变换。
3. **导出自动生效**：`WinPin::getImagePixels` 走的是离屏 `paint(ctx)`，与屏幕绘制同一条路径，旋转不需要额外处理导出。
4. **旋转手柄**：新增一个 dragger（放在 `rect` 上方一段距离），拖拽时按 `atan2` 更新 `angle`；`paintDragger` 里的虚线框也要跟着旋转绘制。
5. **命中判定要改**：`ShapeText::mouseMove` 现在是轴对齐的 `rect` 判定，旋转后必须把鼠标点绕中心**逆旋转**回本地坐标再判定，否则框转了但点击区域还停在原处。

**⚠️ 唯一的硬约束（必须提前决定取舍）**：`WinPin.h` 的注释已经写明——**编辑中的文字是 `TextBox` 这个真控件画的，D2D 变换管不到它**（缩放功能当年就撞过这堵墙，最后靠 `ShapeText` 自己乘 `scale` 解决）。旋转后这个问题更麻烦，因为旋转没法靠乘一个数糊弄过去。

三种取舍，推荐第一种：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）** | 进入编辑时临时把角度归零，TextBox 水平显示；退出编辑后恢复旋转 | 编辑瞬间文字会「摆正」一下，提交后又转回去。可接受，且与现有缩放问题的处理思路一致 |
| B | 编辑态不旋转，把 TextBox 摆在旋转后包围盒的位置 | 编辑框位置与最终位置有偏差，容易让用户困惑 |
| C | 让 Ling 支持旋转控件 | Ling 是自研可控上游，技术上可行，但改动面大，性价比不如 A |

**成本**：中等。旋转本身不难，主要工作量在编辑态取舍与命中判定的逆变换。

### 需求 4 — 支持横向滚动截图

**代码现状**：`Win/CapLong.cpp`（455 行）**完全写死 Y 轴**。所有关键符号都是纵向的：`changeStartY`（变化起始行）、`resultH`（累积高度）、`toGrayscale(img1.data() + changeStartY * rowPix, ...)`（按行比对）、`stripH`（纵向条带）、`reachedBottom` / `tooLong` 两个语言键。预览拼接 `makeImgPreview` 也按 `resultH` 纵向铺。

**✅ 可行，成本中等 —— 是一次对称重构，不是新增模块**

改造路径：
1. **匹配轴参数化**：把 Y 轴逻辑抽成`横向/纵向`两个分支（或转置矩阵），新增 `changeStartX`、`resultW`。核心算法 `findScrollByBottomStrip` 需要一个横向版本（按列比对条带 `stripW`）。
2. **到底判定**：`long.reachedBottom` 语义扩展为 `reachedEdge`，横向也复用；`long.tooLong` 同理改判 `resultW`。
3. **触发方式（关键难点）**：纵向靠 `WM_MOUSEWHEEL` 自然触发，横向没有等价的默认手势。建议采用 **Shift + 滚轮** 或 **方向键**，并复用已有的 `WinCap::hollowWin()` 让消息穿透到底层窗口（这个机制纵向已经跑通了，横向可直接复用）。
4. **工具条**：`ToolLong` 需要一个方向切换入口（`--enter=long` 命令行参数可加 `--long-axis=x` 用于脚本化）。

**⚠️ 风险**：横向拼接的比对条带比纵向窄很多（选区高度通常远大于宽度），**误匹配率会显著高于纵向**。建议对横向模式在选区尺寸上给出约束提示（例如宽度不低于 N 像素），并在拼不上时给出明确失败提示，而不是静默产出错位长图。

### 7.5 排期逻辑（按裁剪后的范围重排）

1. **A 在最前**：全部无依赖，产出可见，且 A1（容器）是后续所有标注能力的挂载点——容器不先理顺，以后每加一个功能都要重新纠结往哪塞。
2. **B 紧随其后但不能再晚**：G1（WinPin 多实例）风险最集中。太早动它，用户长期看不到成果且走偏返工面大；太晚动它，WinPin 会被后续需求反复修改。放在 A 之后正好。
3. **C 是本路线的战略重心**：贴图体系是 PixPin 最大的产品差异点，也是 tpix 目前空白最大的一块。**F 组取消后，资源应更多集中到 C 组**，不再被 FSCapture 方向的编辑器牵扯。
4. **D 排在 B3 之后**：D1/D2 依赖 G5 内置 OCR 落地。**但 D4 不依赖 G5 的网络部分（HTTP/HTTP 层自成一系），S1 云端对话可与 B/C 组并行；S2 取词翻译依赖 G5 的 OCR 词框坐标。**
5. **E/G/H 后置**：属深化项。裁剪后 E 剩 4 项、G 剩 2 项、H 剩 4 项，量级可控，可与 C 组并行推进。
6. **H6 只剩水印**，工作量由 XL 降为 M，**建议提前到 A 组之后紧接执行**，因为水印本身就是一个标注工具，可直接挂在 A1 理顺好的容器上。

### 7.7 如果只能做一件事

**做 A5（输出格式与自动保存）。** 成本最低、无依赖、直接消掉最高频的体验断点。

如果可以做三件事：**A5 + A1 + A2**——保存不再打断、容器理顺、序号补齐，产品完成度会有肉眼可见的跃升。

如果要真正对标 PixPin：**必须做 B1 + C 组**。贴图体系是 PixPin 的产品灵魂，tpix 在这一段目前是完全空白，其余所有能力的补齐都换不来同等的定位提升。

## 八、一句话总结

tpix 差的不是截图本身，而是**截图之后的那条链路**——竞品在"图产出后怎么用、怎么存、怎么回查、怎么贴在工作面上"花了绝大部分力气，而 tpix 在这一段几乎是空白。

在**只对齐 PixPin、暂不接 FSCapture 能力**的裁决下，本轮路线收敛为：

**A 组（容器、序号、智能擦除、文字旋转、输出保存）快速补齐可见短板 → B 组地基（WinPin 多实例、历史/剪贴板记录、内置 OCR）→ C 组贴图体系 + H6 水印 → D 组（D4-S1 云端对话 → OCR 多语种 → 表格识别 → D4-S2 取词翻译 → D4-S3 火山链路）→ E/G/H 剩余深化项。**

两个不可动摇的判断：

1. **B1（WinPin 多实例）+ C 组（贴图体系）不可跳过**。贴图是 PixPin 的产品灵魂，tpix 在这一段完全空白，其余能力的补齐都换不来同等的定位提升。且 F 组（FSCapture 编辑器方向）取消后，资源应更集中地投到这里。
2. **B3（内置 OCR）是本轮必做**（用户点名）。它是把 tpix 从"截图工具"推向"信息工具"的分水岭，也是 D1/D2 的唯一地基。
