## 0. 结论摘要

| 项 | 决定 |
| --- | --- |
| 本期做什么（P1-a） | 停录后进**编辑窗**：预览播放 + **头尾裁剪（帧级）** + 导出 / 复制 / 丢弃 |
| 本期不做 | GIF 编辑、区域放大标注（随时间变化的缩放）、中段多段删除（留 P1-c/P2） |
| 技术路线 | **MediaFoundation 转码**：`IMFSourceReader`（解码）→ `IMFSinkWriter`（重编码 H.264/HEVC + AAC） |
| 为什么不做无损裁剪 | 见 §3.1 —— tpix 的 mp4 由 MF muxer 产出，自研 box 级重写既脆弱又只能切到关键帧 |
| 入口 | 默认「停录 → 编辑窗」；原「直接保存」保留为编辑窗内一条快捷路径（可关） |
| 新窗口 | `WinVideoEdit`（`Ling::WinBase` 单例，同 `WinAiChat`），不进 `WinCap` 的 stage 体系 |

## 1. 现状（以代码为准）

```
ToolVideo::saveFile()       停录 → win->stopRecord() → 空路径则直接 close
                            → Util::getSaveFilePath() 弹保存框 → CopyFile → DeleteFile(temp) → close
ToolVideo::finishRecord(剪贴板) 停录 → Util::addFileToClipboard(temp) → close（temp 留给剪切板）
CapVideo::stop()            卸钩子 → 藏遮罩 → MustEnd → join 采集线程 → 返回 temp.mp4 / temp.gif
                            帧数为 0 时删文件返回空串
CapVideo::startMp4()        DXGI 桌面复制 → VideoMp4::DesktopCapture()（内部 IMFSinkWriter）
                            编码器 HEVC → H.264 逐个回退；宽高对齐 4/2
```

三个前提事实（决定了路线）：

1. **产物位置**：`Setting::getDataPath() + L"temp.mp4"` / `temp.gif`，编辑期间由我们独占。
2. **`VideoMp4.hpp` 只有"采集→编码"一条路**：`CAPTURE` + `DesktopCapture()` + `IMFSinkWriter`，
   **没有任何读回 / 解码 / 解析能力**（已全文确认）。
3. **产物是标准 MP4**（MF muxer 写的），所以系统解码器一定读得回来 —— 这是选 MF 转码的前提。

## 2. 范围分期

| 期 | 内容 | 状态 |
| --- | --- | --- |
| **P1-a** | 编辑窗 + 头尾裁剪 + 导出/复制/丢弃 + 预览播放 | 本期做 |
| P1-b | 画幅裁剪 / 等比缩放（导出分辨率与录制不同） | 预留（转码管线里加一层 `MFVideoProcessor` 即可，接口先留好） |
| P1-c | 区域放大标注（某时间区间内放大某块区域，教程刚需） | 建议 P2 —— 要"随时间变化的变换"，是每帧变换 + 关键帧插值，成本远高于前两项 |
| — | GIF | **不做编辑**。GIF 是自己的编码器、8bit 调色板，改帧要重做量化与调色板；且 GIF 上限 6 分钟、定位是"小片段"，编辑价值低 |

## 3. 技术路线

### 3.1 为什么不走"无损关键帧裁剪"

- 无损裁剪 = 只保留部分样本、重写 `moov/stbl` 索引、时间戳平移。**必须自研 MP4 box 解析 + 重写**，
  而 tpix 的 mp4 是 MF muxer 产出（`VideoMp4.hpp` 无解析器），等于新引入一个脆弱组件。
- 精度受 GOP 限制：H.264 硬编 GOP 常在 1–2 秒，裁不到用户拖的那个位置，观感就是"剪不准"。
- 收益只有"不重编码"，但 1080p 硬编转码通常快于实时，用户等 1~2 秒无感。

### 3.2 选定的管线（MF 转码）

```
temp.mp4 ──IMFSourceReader──┬─ 视频：解码 → (可选 VideoProcessor 缩放/裁画幅) → NV12/RGB32
                            └─ 音频：解码 → PCM（重采样到编码器要求的格式）
                                   ↓
                      时间过滤（pts < in 丢；pts > out 停）
                                   ↓
                    IMFSinkWriter ── H.264/HEVC（硬编优先）+ AAC ──→ 新 mp4
```

要点：

- **裁剪**：`IMFSourceReader::SetCurrentPosition(in - 余量)` 先 seek（MF 自动落到关键帧），
  然后**丢弃 pts < in 的样本、pts > out 后停止**。因为整段重编码，精度就是帧级，与 GOP 无关。
- **音频对齐**：视频/音频各按自己的 pts 裁；AAC 帧长 1024 样本（~23ms），起止各允许半帧误差。
  导出后校验 `|视频时长 - 音频时长| < 1 帧` —— 这是最容易出错、必须进验收的一条。
- **编码参数继承录制**：分辨率、fps、码率（`vbrm=2 / vbrq=50 / Qu=50`）照搬 `startMp4` 的取值；
  `MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS` 打开，硬编不可用时 MF 自动回退软编（慢，但可用）。
- **HEVC → H.264 回退**：复用 `CapVideo::startMp4` 里那套"targets 逐个试 / 编码器逐个试"的写法，
  逻辑同源（可抽成一个共用函数，但**不要**为省事把录制路径也重构成转码路径）。

### 3.3 预览：与导出共用同一条解码链

- 预览**不是**另找一个播放器控件，而是"按当前时间点向解码器要一帧，画到自绘画布上"，
  播放态由 `Ling` 定时器（33ms）推进 —— 与导出用的是同一套解码配置，**所见即所得**。
- 画布复用 `WinHistory.cpp` 里 `CoverImage` 那套（`Ling::Canvas` 子类 + `ID2D1Bitmap1`），
  两处差异：
  1. 编辑预览用 **contain**（整帧可见，便于看裁剪点），不是 cover；
  2. **位图只建一次、逐帧 `CopyFromMemory`**（每帧 `CreateBitmap` 等于每帧 8MB 分配 + 拷贝，
     1080p 下会明显掉帧）。
- ⚠️ 画布后端：预览画布窗口尺寸固定，可用默认 `CompositionDrawingSurface`；**一旦要支持
  "随窗口缩放重排"就得 `enableSwapChain()`**（默认后端尺寸一变内容即清空，见 TOPIC-ling-ui §11）。

## 4. UI 与交互设计

### 4.1 窗口形态

独立窗口 `WinVideoEdit`（约 900×620 逻辑像素，居中、可拖动、**不置顶**）：
进编辑窗时 `WinCap` 已经 `close()`（与现状一致：录完整个截图流程收工），所以不存在"压在录制区上"的问题。

```
┌──────────────────────────────────────────────────────────┐
│ 录制完成 · 03:12                                   ✕     │  头带 40px
├──────────────────────────────────────────────────────────┤
│                                                          │
│                  [ 预览画面（contain） ]                  │  预览区 flexGrow
│                                                          │
├──────────────────────────────────────────────────────────┤
│  ▶ 00:00:42 / 03:12        [———▓▓▓▓▓▓▓▓————]             │  时间轴
│    起点 00:12.30   终点 02:44.10   裁剪后 02:31.80        │  读数行
├──────────────────────────────────────────────────────────┤
│ [导出]  [复制到剪贴板]        [直接保存原片]   [丢弃]     │  按钮条 48px
└──────────────────────────────────────────────────────────┘
```

### 4.2 控件与行为

| 控件 | 行为 |
| --- | --- |
| 预览画面 | 单击 = 播放/暂停；点击处**不动**裁剪点（避免误改） |
| 时间轴 | 一条轨道 + 两个手柄（in/out）+ 一个播放头。拖手柄 = 改裁剪点；拖中间 = 移动播放头；把手柄拖到对侧 = 交换 |
| 播放头 | 播放时跟随；暂停时拖它 = 逐帧预览（seek 到目标帧） |
| 读数行 | 起点 / 终点 / 裁剪后时长（`mm:ss.cc`，1/100 秒） |
| 导出 | 转码 → 完成后弹 `Util::getSaveFilePath()`（沿用现有保存框）→ 成功则删临时文件并关窗 |
| 复制到剪贴板 | 转码到临时文件 → `Util::addFileToClipboard()`（与现状同款；剪切板持有路径，所以**删**的是原始 temp） |
| 直接保存原片 | 原行为：不转码，直接保存框 + `CopyFile` |
| 丢弃 | 删临时文件 → 关窗 |
| ✕ / ESC | 关窗。**保留临时文件**（用户可能误触），下次进编辑窗仍可找回；临时文件随下次录制覆盖 |

## 5. 关键实现决定（后人别改）

1. **预览与导出共用解码参数**：两处各写一遍迟早会分叉成"预览对、导出错"。
2. **编辑期间不删临时文件**：`CapVideo::stop()` 返回路径后所有权归编辑窗；只有"导出成功 / 丢弃 /
   重新录制"三条路会删它。
3. **不倒放**：MF `SourceReader` 无反向解码。逐帧后退 = seek 到目标时间再解到目标帧，代价 O(GOP)。
   拖动播放头要**节流**（同 `WinAiChat` 流式重画的 33ms 节流思路），否则拖动时把解码器拖死。
4. **转码线程**：与 `CapVideo` 同款 `std::jthread` + 进度回调（进度用 `IMFSinkWriter` 的
   `MF_SINK_WRITER` 编码时间 / 总时长估算），UI 侧只更新一个进度条。
5. **失败要给话**：转码失败（解码器缺失 / 硬编失败且软编也失败）必须弹提示（复用
   `CapVideo.cpp` 里 `showRecordError` 的形态），**不能**静默收场 —— "录完什么都没有"是历史雷区。

## 8. 风险与验收

| 风险 | 对策 |
| --- | --- |
| 硬编不可用 ⇒ 软编慢 | 进度条 + 可取消；>2 分钟的视频给"预计耗时"提示 |
| 音视频不同步 | 起止各自裁 + 导出后校验时长差 < 1 帧 |
| 拖动播放头卡顿 | 节流 + 拖动期间降采样解码（每 N 帧解一帧） |
| 长视频（上限 120min）内存 | 全程流式，不整段读进内存；预览只保留当前帧 |

**验收（探针可自动化的部分）**：造一段 5 秒 30fps 的录制 → 裁掉头 2 秒、尾 1 秒 → 导出 →
① 时长 ≈ 2.0s（±1 帧）；② 首帧内容等于原视频第 60 帧（拿截图比对）；③ 音视频时长差 < 1 帧；
④ 编辑窗关闭后临时文件仍在，丢弃后文件消失。
